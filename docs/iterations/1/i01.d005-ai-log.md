## Pools containing Bets ([#29](https://github.com/MESW-LES-2627/les-project-group-8/issues/29))

- **Who:** João Luiz Cerqueira.
- **Tool:** Codex 6.1 Sol
- **What we asked:** Implement our plan for the new database schema that separates bets from pools, creating pools as a "group" containing the bets, and then implement frontend and backend to reflect this change.
- **Decisions we made:** We decided the DB schema. We decided pool should contain a deadline for all bets created, a decider, a description and a name, plus N bets. The bets table should contain the statement, and the presentation(radio or dropdown). The foreign keys such as winnining_outcome_id for bets or creator_id for the pool table, was already part of the previous design, where pools and bets were "unified" (a pool had a single bet, so the table columns were merged). The division was of our choice too.
- **Where we intervened / mistakes the AI made:** We repeatedly narrowed the scope and asked for smaller PRs, reviewing each part before authorizing commits and pushes. We removed repository tests that added maintenance without enough value, in fact, by the end i had removed more than 10 tests that brought no real value and were testing "data migration" scenarios that were never going to happen but for the 1st data migration. The AI also rewrote older user stories to match the new implementation and inserted issue history into the requirements document. We asked it to preserve the original requirements and describe the expanded structure in E7. It then overcorrected by removing the introduction and changing the status categories, which we also had to correct. The AI removed error handling randomly during frontend implementation
- **How we checked it:** We reviewed the diffs throughly. The CI ran the backend tests and frontend checks. We then tested the deployed features on staging.

My conclusion is that AI helped implement changes across several layers, but needed clear boundaries and frequent review. Planning against the current code and separating the work into small PRs made its decisions easier to inspect.

## Psycopg and transactions when creating a pool (https://github.com/MESW-LES-2627/les-project-group-8/pull/57)
- **Who:** Denis Dunaev
- **Tool:** Codex GPT-6.1 Sol
- **What we asked:** Help to replace the backend’s Supabase Data API repositories with Psycopg while retaining Supabase-hosted PostgreSQL and Supabase Auth. Make Pool creation and adding a Bet with its options atomic, document local/staging configuration, and verify rollback and successful subsequent requests using real PostgreSQL. Adapt the implementation to the team’s latest changes.
- **Decisions we made:** We retained the existing Pool/Bets model and authentication flow from staging. Bets represent questions, so a separate Question model was unnecessary. We kept one internal initial round per Pool without introducing round-management endpoints or UI. Optional initial_bets allows a Pool, its round, Bets and options to be saved in one transaction, while preserving the frontend’s existing empty-Pool creation flow. All three repositories—Users, Pools/Bets and Picks—use Psycopg. Database credentials are configured through DATABASE_URL, while SUPABASE_URL remains necessary for Auth.
- **Where we intervened / mistakes the AI made:** The initial implementation introduced more structure and supporting code than we wanted, including a separate Question model, additional endpoints, a database-check command and a standalone smoke script. We asked the AI to reduce the scope. The AI then removed the obsolete guest-based logic and adapted persistence to authenticated Users, Bets and Picks.
- **How we checked it:** We inspected the changes against staging. All 114 backend tests passed locally, including real PostgreSQL rollback tests and the existing remote Supabase RLS tests. Forced failures during option insertion confirmed that partial creation was rolled back, existing Bets and Picks remained unchanged, and subsequent valid requests succeeded. Frontend type checks and the production build passed. A local form flow covered login, Pool creation, adding a dropdown Bet, saving/replacing a Pick and refreshing pages, using real PostgreSQL and a temporary ES256 Auth test service. Hosted Auth and deployment verification on staging, plus teammate review, remain outstanding.
  
My conclusion is that AI helped implement and test changes across the persistence layer, configuration and documentation, but needed clear scope limits and checks against the team’s current code and passing local tests was useful evidence.
