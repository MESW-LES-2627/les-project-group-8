## Pools and Bets (issue #29)

See [ADR 0004](../../adr/0004-pools-contain-bets.md) for the design decisions.

- `pools` holds the name, description, creator, decider, creation date and shared
  deadline. A new Pool has no Bets; only its creator can add them before the deadline.
- `bets.pool_id` links each Bet to its Pool. `bets` holds the statement,
  presentation (`radio` by default, or `dropdown`) and optional winning Outcome.
- `outcomes.bet_id` links each option to its Bet.
- `outcomes.position` stores the authored order, starting at 0. The repository
  sorts by it so clients receive options in the order the organizer entered them.
- A Bet has between 2 and 10 options. Uniqueness and non-empty labels are
  enforced by `pools/service.py`; the frontend mirrors the same rules.
- `picks` stores one answer per `(bet_id, user_id)`. A second submission
  replaces the row (`UNIQUE (bet_id, user_id)`), so changing a Pick never
  duplicates it. The participant is the logged-in User from the access token; the
  API refuses a `user_id` in the body. The service refuses picks once the deadline
  has passed or that Bet already has a winner.
- Composite foreign keys ensure a Pick and a winning Outcome refer to an
  Outcome of the same Bet. Deleting a Pool cascades to its Bets, Outcomes and Picks.

Row-level security is enabled without policies on `users`, `pools`, `bets`,
`outcomes` and `picks` by migrations 003 and #29. Flask connects with the secret
key, which bypasses RLS (ADR 0003); the frontend never accesses these tables directly.

The #29 migration creates one Bet per existing Pool, reusing the old Pool ID.
It preserves Pool URLs, Outcome/Pick IDs, option order, presentation and winners.
Apply it with the adapted application; verification against staging is still pending.
No Round table is introduced.
