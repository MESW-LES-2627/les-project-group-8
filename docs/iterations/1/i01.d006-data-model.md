## Multiple-choice questions (issue #30)

Until #29 introduces separate questions, a pool is the multiple-choice question.

- `pools.presentation` stores `radio` or `dropdown` and defaults to `radio`.
- `outcomes.position` stores the authored order, starting at 0. The repository
  sorts by it so clients receive options in the order the organizer entered them.
- A question has between 2 and 10 options. Uniqueness and non-empty labels are
  enforced by `pools/service.py`; the frontend mirrors the same rules.
- `picks` stores one answer per `(pool_id, user_id)`. A second submission
  replaces the row (`UNIQUE (pool_id, user_id)`), so changing a pick never
  duplicates it. The participant is the logged-in User from the access token; the
  API refuses a `user_id` in the body. The service refuses picks once the deadline
  has passed.

`003_enable_rls.sql` turns row-level security on for `users`, `pools`, `outcomes`
and `picks` with no policies. Flask connects with the secret key, which bypasses
RLS (ADR 0003); the frontend never talks to these tables directly.

When #29 lands, `presentation` and `outcomes` move under the question, and
`picks.pool_id` becomes `picks.question_id`. The current shape is a deliberate
interim step so #30 can ship without waiting for the structural refactor.
