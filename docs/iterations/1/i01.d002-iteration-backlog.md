# Next Iteration

The four issues below are selected for this iteration. Each functional issue
covers frontend and backend together, with tests, PR and review.
The [complete backlog](i01.d001-user-stories.md) contains the wider product scope.

## 1. Authentication with Supabase

**Stories:** As a user, I want to sign in with my own account and see my identity,
so that the pools and predictions I create belong to me.

**Tasks:**

- [ ] Add email/password login, logout and the current user's name in the UI.
- [ ] Restore sessions after reload and handle expired sessions. Use individual
  accounts and application profiles created beforehand in Supabase.
- [ ] Validate authentication in the backend and derive ownership from the
  logged-in user. Remove the shared Guest User as the identity for new writes.
- [ ] Require login to create pools or submit predictions; keep public browsing.
- [ ] Test the flow with two accounts and reject unauthenticated requests or
  attempts to impersonate another user by changing an ID.

**Acceptance:** each account can log in, reload, create its own pool and log out;
frontend and backend consistently use the correct identity.

## 2. Turn pools into groups containing questions

**Stories:** US25 — Create a pool as a group of questions; US8 — Open a pool.
As an organizer, I want related questions inside one pool so that an event has
one shared place.

**Tasks:**

- [ ] Give the pool its own name, description, creator and creation date,
  separate from each question's prompt, type and answer options.
- [ ] Introduce a round containing the questions and their prediction deadline.
  Use one round per pool in this iteration; multiple rounds remain in the backlog.
- [ ] Adapt creation and detail pages so the organizer can create a pool and add
  questions, and participants can view those questions within the same pool.
- [ ] Adapt the backend, database and frontend types to the new structure,
  preserving existing pools and their question/option associations.
- [ ] Test creation, adding a second question, listing/detail views and migration
  of the existing single-question pools.

**Acceptance:** after reload, one pool displays its own information and at least
two independent questions. Existing data remains accessible.

## 3. Multiple choice with two or n options, including dropdowns

**Stories:** US26 — Multiple choice with n options; US27 — Dropdown presentation;
US10 — Pick an outcome; US12 — See my pick.
As an organizer, I want flexible answer options; as a participant, I want to
choose one and see that my prediction was saved.

**Tasks:**

- [ ] Allow the organizer to add/remove options while creating a question,
  supporting both exactly two and more than two options.
- [ ] Validate at least two distinct, non-empty options in frontend and backend,
  and preserve their order when saving and displaying them.
- [ ] Let the organizer choose radio buttons or a dropdown and persist that choice.
  Both presentations select exactly one answer; a dropdown starts with no answer.
- [ ] Save the authenticated participant's choice for the specific question and
  restore it after reload. Reject unrelated options and submissions after closing.
- [ ] Test binary and n-option questions in both presentations, including invalid
  options and independent answers to different questions in the same pool.

**Acceptance:** participants can answer questions with two or more options,
using radio buttons or a dropdown, and their saved answers survive a reload.

## 4. Psycopg and transactions when creating a pool

**Stories:** technical fix supporting pool creation (US2 and US25).

**Tasks:**

- [ ] Replace the backend's Supabase Data API repositories with Psycopg. Keep
  PostgreSQL hosted on Supabase and Supabase Auth for authentication.
- [ ] Save a new pool, its initial round, questions and options in one transaction:
  either everything is saved or nothing is saved. Replace cleanup by deletion.
- [ ] Make adding a question and its options atomic as well, without changing
  the pool's existing questions if that addition fails.
- [ ] Configure the backend database connection and document local/staging setup.
- [ ] Use a real PostgreSQL test database to force a failure partway through
  creation and confirm rollback. Check that subsequent valid requests succeed.

**Acceptance:** a failed creation leaves no partial pool, round, question or  
options; a valid creation persists the complete structure and remains visible  
through the frontend.
