# Next Iteration

The four issues below are selected for this iteration. Each functional issue
covers frontend and backend together, with tests, PR and review.
The [complete backlog](i01.d003-user-stories.md) contains the wider product scope.

## 1. Authentication with Supabase

**Issue:** #28 (spec #34). **Stories:** US1 — Create an account; US5 — See who I am.
As a person joining the app, I want to create my own Account, sign in and see my
name, so that the pools I create and the Picks I make belong to me.

**Tasks:**

- [x] Add sign-up (email, password, display name), login, logout and the current
  User's name in the UI. Every new Account gets its User automatically.
- [x] Restore sessions after reload and handle expired sessions.
- [x] Validate authentication in the backend and derive ownership from the
  logged-in User. Remove the shared Guest User and the pools that belong to it.
- [x] Require login to create pools or make Picks; keep public browsing.
- [x] Test the flow with two Accounts and reject unauthenticated requests or
  attempts to impersonate another User by changing an ID.

**Acceptance:** each person can sign up, log in, reload, create their own pool and
log out; frontend and backend consistently use the correct User.

**Known gaps (found in the review of #35–#39, not fixed yet):**

- Picks need login too (#28, "Require login to create pools or make Picks"), but
there are no Pick endpoints yet and no issue tracks adding the guard to them.
The Picks module must use `@login_required` from the start. **Resolved by #30:**
the picks endpoints use `@login_required` and derive the participant from the
token.
- `redirectTo` is lost on sign-up (#38): the "Sign up" link on `/login` drops it,
and sign-up always lands on `/`. Someone sent from `/pools/new` who signs up
instead of logging in is not brought back.
- The sign-up form counts the name's length in UTF-16 units (JS `.length`), but
the database `CHECK` counts characters (`char_length`). A name with emoji can be
rejected by the form although the database would accept it. The form is only
ever stricter, never looser.
- When Supabase's key set can't be fetched, Flask answers 500 instead of 401
(`TokenVerifier` re-raises `PyJWKClientConnectionError`). This is deliberate,
since the failure is ours, but #35 does not mention it.
- Manual steps in #36–#39 (applying migrations 003, 003a and 003b, and checking on
staging) happen outside the code and must be confirmed on each PR.



## 2. Turn pools into containers of Bets

**Issue:** #29. **Stories:** US25 — Create a pool as a group of Bets; US8 — Open a pool.
As an organizer, I want related Bets inside one Pool so that an event has
one shared place.

**Tasks:**

- [x] Create an empty Pool with its own name, description, creator, creation date
  and shared deadline. Rounds stay future scope (US29; ADR 0004).
- [x] Let only the creator add Bets before that deadline; display multiple Bets
  and independent authenticated Picks on the Pool page.
- [x] Adapt backend, frontend and migration to preserve existing Pool URLs,
  options, Picks, order, presentation and winners.
- [x] Test creation, multiple Bets, listing/detail, ownership and shared deadlines.
- [x] Apply the migration with the adapted app and verify staging, including
  existing data (US25/US8).

**Acceptance:** after reload, one pool displays its own information and at least
two independent Bets. Existing data remains accessible.

## 3. Multiple choice with two or n options, including dropdowns

**Stories:** US26 — Multiple choice with n options; US27 — Dropdown presentation;
US10 — Pick an outcome; US12 — See my pick.
As an organizer, I want flexible answer options; as a participant, I want to
choose one and see that my prediction was saved.

**Tasks:**

- [x] Allow the organizer to add/remove options while creating a Bet,
  supporting both exactly two and more than two options.
- [x] Validate at least two distinct, non-empty options in frontend and backend,
  and preserve their order when saving and displaying them.
- [x] Let the organizer choose radio buttons or a dropdown and persist that choice.
  Both presentations select exactly one answer; a dropdown starts with no answer.
- [x] Save the authenticated participant's choice for the specific Bet and
  restore it after reload. Reject unrelated options and submissions after closing.
- [x] Test binary and n-option Bets, both presentations, invalid options and
  independent Picks in the same Pool (#29).

**Acceptance:** participants can answer Bets with two or more options,
using radio buttons or a dropdown, and their saved answers survive a reload.

## 4. Psycopg and atomic Bet creation

**Stories:** technical fix supporting pool creation (US2 and US25).

**Tasks:**

- [ ] Replace the backend's Supabase Data API repositories with Psycopg. Keep
  PostgreSQL hosted on Supabase and Supabase Auth for authentication.
- [ ] Make creation of a Bet and its options atomic within an existing Pool;
  replace cleanup by deletion and preserve existing Bets if the addition fails.
- [ ] Configure the backend database connection and document local/staging setup.
- [ ] Use a real PostgreSQL test database to force a failure partway through
  creation and confirm rollback. Check that subsequent valid requests succeed.

**Acceptance:** a failed Bet creation leaves no partial Bet or options; a valid
creation persists both and remains visible through the frontend. Pool creation
stays a separate operation; no Round is introduced.
