# How to run tests

## Running them

```bash
cd backend
python -m venv .venv && source .venv/bin/activate
pip install -r requirements-dev.txt
pytest -v
```

Acceptance tests need no Supabase credentials. The two RLS integration tests skip
unless `SUPABASE_URL` and `SUPABASE_PUBLISHABLE_KEY` are set (see `backend/.env.example`). CI runs the same `pytest -v` on pushes to
`main`/`staging` and pull requests that touch backend code or the "backend/"
(`.github/workflows/backend-ci.yml`). `render.yaml` configures deployment to wait for passing checks.

## What we test, and why

The suite is made of **acceptance tests**: tests check the acceptance criteria from [i01.d003-user-stories.md](./i01.d003-user-stories.md) through the public HTTP API. Payloads are built by test fixtures and the suite does not execute SvelteKit or prove that its actual requests match the API. Tests are written as **Given / When / Then** comments and named after the behavior (`test_pool_naming_its_creator_is_rejected`). The table below links each acceptance criterion to its test.

We test through HTTP because the API is the contract the frontend relies on.
These tests protect the listed behaviors during refactoring and passing them doesn't establish complete OpenAPI conformance or deployed end-to-end functionality.

```
backend/tests/
├── conftest.py                      # fresh app + fake repositories + test token verifier for every test
├── fakes.py                         # in-memory repositories (test doubles)
└── acceptance/
    ├── steps.py                     # sign_in, token helpers, create_pool, create_bet, payloads
    ├── test_us2_create_pool.py      # US2
    ├── test_us3_list_pools.py       # US3
    ├── test_us5_see_who_i_am.py     # US5 backend: GET /api/me and the login guard (#35)
    ├── test_us10_pick.py            # Pick creation/replacement and participant identity
    ├── test_us12_see_pick.py        # US12
    ├── test_us26_multiple_choice.py # US26
    ├── test_us27_dropdown.py        # US27
    ├── test_us29_pool_bets.py       # issue #29 / US25: authoring, shared deadline, Bet boundaries
    └── test_api_conventions.py      # health check, JSON 404 and 500, no POST /api/users
└── integration/
    └── test_rls_back_door.py        # ADR 0003: the publishable key cannot read or insert pools
```

## Fake repositories

`create_app(user_repo=..., pool_repo=..., pick_repo=...)` accepts the repositories it should use. In production it builds the Supabase ones. In tests, `conftest.py` passes in-memory fakes from `tests/fakes.py`, with Pool/Bet creation and reads, and `create_or_replace`/`list_user_picks` for Picks. The fake user repository also has `add`, which `sign_in` uses to seed Users the way the sign-up trigger creates them; the app itself never creates Users.

As a result, everything above the database is real in every test: routes, services, validation, and JSON. The only thing replaced is the storage. Tests are fast, independent, and don't touch the shared Supabase database. The fakes live only in `tests/` and are never used by the running app.

The fakes do not cover Supabase queries, SQL constraints or migration data preservation.
For #29, those still need verification with the coordinated migration/deploy on staging.

## The back door (integration)

`tests/integration/test_rls_back_door.py` is the only part of the suite that talks to the real Supabase project. It uses the publishable key, which is public by design, to read and insert `pools` straight through Supabase's REST API, and checks that row-level security refuses both (ADR 0003). The two refusals look different: with no policies, RLS **filters reads** (200 with no rows) but **rejects writes** (Postgres error `42501`). The insert names a User that does not exist, so even if RLS were turned off the foreign key would stop the row being saved and the test would fail with `23503` instead. When the secret key is also set (as in a local `backend/.env`), the read test first checks that pools exist, so an empty answer proves something; CI only has the publishable key and skips that check. Both tests skip when `SUPABASE_PUBLISHABLE_KEY` is not set.

## Access tokens

`create_app(..., token_verifier=...)` also accepts the verifier for Supabase access tokens. `conftest.py` passes one that trusts a throwaway ES256 key pair generated in `tests/acceptance/steps.py`, and the steps sign real tokens with its private half, so the real verification runs. `sign_in(user_repo, name)` seeds a User in the fake repository and returns it with valid auth headers. `expired_token`, `wrong_audience_token` and `forged_token` (signed by a key the app doesn't trust) build the invalid variants.

Fetching Supabase's published key set (`TokenVerifier.from_env()`) is not covered automatically. It was checked by hand against a local JWKS server: repeated tokens caused one fetch, and a token with a new `kid` caused one refetch.

The pick endpoints reuse the same login guard as pool creation: no token or an
invalid token gets 401, and a valid token whose Account has no User gets 403
(`test_us10_pick.py`). The pick/detail user interface is verified manually:
create an empty Pool, add a radio Bet and a dropdown Bet, save Picks on both,
reload, and change one without changing the other. Repeat with a second User
to check that saved Picks and authoring controls belong to the correct User.

The #29 stack passed 107 tests (including both Pool RLS checks) and this local
browser flow with in-memory storage. Staging verification and the shared
database migration remain pending; rounds are not implemented.

US1 (sign-up) is checked by hand on staging; its old `POST /api/users` tests were removed with the endpoint in #39, and `test_api_conventions.py::test_users_cannot_be_created_through_the_api` checks it is gone. AC 2.11 (the create-pool page sends logged-out visitors to login and back) is a frontend behavior, checked by hand until #33. A valid token whose Account has no User gets 403 on `POST /api/pools` too (`test_pool_for_an_account_without_a_user_is_forbidden`).
