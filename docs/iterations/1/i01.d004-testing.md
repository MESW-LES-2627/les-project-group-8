# How to run tests

## Running them

```bash
cd backend
python -m venv .venv && source .venv/bin/activate
pip install -r requirements-dev.txt
pytest -v
```

No Supabase credentials are needed. CI runs the same `pytest -v` on pushes to
`main`/`staging` and pull requests that touch backend code or the "backend/"
(`.github/workflows/backend-ci.yml`). `render.yaml` configures deployment to wait for passing checks.

## What we test, and why

The suite is made of **acceptance tests**: tests check the acceptance criteria from [i01.d003-user-stories.md](./i01.d003-user-stories.md) through the public HTTP API. Payloads are built by test fixtures and the suite does not execute SvelteKit or prove that its actual requests match the API. Tests are written as **Given / When / Then** comments and named after the behavior (`test_unknown_creator_is_rejected`). The table below links each acceptance criterion to its test.

We test through HTTP because the API is the contract the frontend relies on.
These tests protect the listed behaviors during refactoring and passing them doesn't establish complete OpenAPI conformance or deployed end-to-end functionality.

```
backend/tests/
├── conftest.py                      # fresh app + fake repositories + test token verifier for every test
├── fakes.py                         # in-memory repositories (test doubles)
└── acceptance/
    ├── steps.py                     # reusable "Given" steps: sign_in, token helpers, pool_payload
    ├── test_us2_create_pool.py      # US2
    ├── test_us3_list_pools.py       # US3
    ├── test_us5_see_who_i_am.py     # US5 backend: GET /api/me and the login guard (#35)
    └── test_api_conventions.py      # health check, JSON 404 and 500, no POST /api/users
```

## Fake repositories

`create_app(user_repo=..., pool_repo=...)` accepts the repositories it should use. In production it builds the Supabase ones. In tests, `conftest.py` passes in-memory fakes from `tests/fakes.py`, which have the same methods (`get`, `create_pool`/`list_pools`). The fake user repository also has `add`, which `sign_in` uses to seed Users the way the sign-up trigger creates them; the app itself never creates Users.

As a result, everything above the database is real in every test: routes, services, validation, and JSON. The only thing replaced is the storage. Tests are fast, independent, and don't touch the shared Supabase database. The fakes live only in `tests/` and are never used by the running app.

What the fakes cannot catch are errors in the Supabase queries themselves (for example, a wrong column name). Those are checked manually against the staging database for now.

## Access tokens

`create_app(..., token_verifier=...)` also accepts the verifier for Supabase access tokens. `conftest.py` passes one that trusts a throwaway ES256 key pair generated in `tests/acceptance/steps.py`, and the steps sign real tokens with its private half, so the real verification runs. `sign_in(user_repo, name)` seeds a User in the fake repository and returns it with valid auth headers. `expired_token`, `wrong_audience_token` and `forged_token` (signed by a key the app doesn't trust) build the invalid variants.

Fetching Supabase's published key set (`TokenVerifier.from_env()`) is not covered automatically. It was checked by hand against a local JWKS server: repeated tokens caused one fetch, and a token with a new `kid` caused one refetch.
