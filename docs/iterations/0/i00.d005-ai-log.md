## Backend reorganization into a modular monolith ([#11](https://github.com/MESW-LES-2627/les-project-group-8/issues/11)) ([#13](https://github.com/MESW-LES-2627/les-project-group-8/issues/13))

- **Tool:** Cursor agent (Claude).
- **What we asked:** Organize the backend into a simple modular monolith with no over-engineering, remove the in-memory Supabase fallback, and keep the API contract unchanged. We made the decision of having DDD design, with pool and user for now. For each domain module we have the same four files (`routes`, `service`, `repository`, `models`), a `shared/` folder for the database client and errors, and `app.py` reduced to wiring. This happened because previous iteration of the code was becoming AI slop, with nonsense such as "In memory storing as database fallback", complete unorganized code, db native functions for inserting pools, no difference between handler layer, business layer and db layer. Also too much overengineering for the first iteration, unexplainable regex, complex test suite with no really planning. So we had to sit down and decide an archicture to follow, which was the modular monolith.
- **How we checked it:** The existing test suite (35 tests) passes against the new structure. A manual run against Supabase returned 200 for `GET /api/pools` (an empty list). Also a manual check reading that everything was conforming.


## Acceptance test suite ([#15](https://github.com/MESW-LES-2627/les-project-group-8/issues/15))

- **Tool:** Cursor agent (Claude).

- **What the AI proposed:** Write the user stories with numbered Given/When/Then acceptance criteria, then one HTTP-level test per criterion with a matching name. The old unit tests (`test_domain.py`) and the unstructured API tests were removed, because every rule they checked is now covered through the API.
- **Agreed in the plan we approved:** Keep the fake repositories so tests don't need Supabase. Accept that the Supabase queries themselves are only checked manually for now (documented in `i00.d004-testing.md`). We focused on acceptance tests for the vertical slice, as they are a solid start for the simplicity. More complex testing will be considered in the future
- **How we checked it:** 36 acceptance tests pass, and every acceptance criterion in `i00.d003-user-stories.md` maps to one test.

## Frontend pool list and creation form ([#19](https://github.com/MESW-LES-2627/les-project-group-8/issues/19)) ([#20](https://github.com/MESW-LES-2627/les-project-group-8/pull/20))

- **Tool:** OpenCode (DeepSeek V4.1 Flash).
- **What we asked:** The frontend half of the iteration 0 slice: list pools and create one against the Flask API. Plain Tailwind, black and white, no rounded corners. We planned first and approved the plan before writing code.
- **What the AI proposed:** Server-side `load` and a form action, a server-only API client so the browser never calls Flask, and a separate `/pools/new` route so the form works without JavaScript. Validation in the action, deadlines in UTC, and quick presets (+1 hour / +1 day / +1 week).
- **Where we intervened / what changed:** We changed the first plan from one page to a separate route and set the visual direction. We chose to trust the backend's `status` instead of deriving it in the UI. Local verification also forced a fix outside the PR: `backend/.env` used the publishable Supabase key, so RLS hid every row, and we switched it to the `service_role` key.
- **Assumptions we accepted:** The local backend runs on 5001 because macOS AirPlay owns 5000, `API_URL` stays optional at build time so CI can build without it, a pool still has exactly two outcomes, and the backend keeps using the guest user.
- **Mistakes the AI made:** The first version had the wrong relative import depth and CSS path, caught by `pnpm check` and `pnpm build`. It also left a real "Stack check" pool in the shared Supabase project.
- **How we checked it:** `pnpm check` and `pnpm build` pass. Created a pool through the form → Flask → Supabase and saw it on `/`; invalid submissions showed inline errors and wrote nothing. The form also works without JavaScript (`curl`). After the merge, `pytest` passes (36 tests).
