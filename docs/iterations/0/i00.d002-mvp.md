# MVP

A web application where users can create prediction pools for friends. The creator specifies the question, deadline, and possible outcomes. The creator and their friends choose their outcome before the deadline. Once the event occurs, the creator resolves the pool by picking the winning outcome. Everyone can track their tally of right and wrong predictions on a personal scoreboard.

This describes the target MVP across iterations. The smaller first-deadline
deliverable is defined in [Thin Vertical Slice (Iteration 0)](#thin-vertical-slice-iteration-0).

## Who is it for?

Groups of friends who create casual, zero-money prediction pools on real-life events (sports, reality TV, personal bets) and want a single place to settle who was right and track their win/loss record.

## MVP Outcomes (What the user can do)

1. **Make a pool.** Set the title, terms, deadline, and choices.
2. **Join a pool.**
3. **Pick a choice.** Lock it in before time is up.
4. **Resolve it.** The creator marks the winner when the event ends.
5. **Track your score.** See your wins and losses.

### Core User Journey (MVP Path)

1. **User A** creates a pool with a title, description/statement, deadline, and distinct outcomes.
2. **Friends** open the pool link, view the details, and select their chosen outcome before the deadline expires.
3. Once the event concludes, **User A (the creator)** resolves the pool by selecting the winning outcome.
4. The pool status updates to `RESOLVED`, and everyone can see who picked correctly and their updated scoreboard.

## What Is Out (Saved for the Vision)

1. **Third-party deciders**: Assigning a separate user (User B) as referee is out for the MVP; the pool creator resolves the pool. The schema retains `decider_id`, the backend service sets it to `creator_id` during creation. This is an application rule, not a database column default.
2. **Guest-to-Account upgrades**: Users either use a basic account or a mocked/guest session—no complex account migration flows.
3. **Weighted pools & custom rewards**: Every pool counts as 1 point (right or wrong). No dynamic odds or custom prize pools.
4. **Real money or payment gateways**: Strictly bragging rights.
5. **Multiple-select pool**: Allowing users to select more than one outcome.
6. **Participant-supplied outcomes**: Participants cannot add outcomes to an existing pool. The creator supplies the labels when creating it. The restriction to exactly two outcomes applies to the Iteration 0 slice below.

## Thin Vertical Slice (Iteration 0)

- **The Flow**: A visitor opens the web app, fills out a form to create a pool with two outcomes and a future deadline, saves it to the database, and sees the newly created pool in the listing with derived status (`OPEN`). The frontend sends the pre-seeded Guest User's `creator_id`; the backend checks that the user exists and sets the decider to that same user.
- **Guest identity**: `backend/migrations/001_init.sql` seeds Guest User with id `00000000-0000-0000-0000-000000000001`. The frontend must include that id in `POST /api/pools`; the backend does not supply a default creator.
- **Supporting API**: `POST /api/users` can create a named user. It is tested as a backend capability, but a user-creation screen is not required for the guest-based Iteration 0 demonstration.
- **Boundary**: Login, picks, pool resolution, scoreboard, and notifications are outside this first-deadline flow.
- **The Stack Check**: Proves the complete stack end-to-end:
  - Frontend UI (SvelteKit 3 on Cloudflare Workers)
  - Backend API (Flask on Render)
  - Database persistence (PostgreSQL on Supabase)

## Definition of Done

1. **Runs on the tag & deployed environment**: Runs cleanly on the `iter-0` git tag and deployed staging servers (`les-frontend-staging.les-h.workers.dev` and `les-backend-staging.onrender.com`), not just on local machines.
2. **Thin Vertical Slice Complete**: A user can create a pool and view the listing end-to-end without errors.
3. **Automated Testing & CI**: All tests (`pytest` for backend API and domain contracts in Backend CI, `pnpm build` in frontend deploy pipelines) pass.
4. **Specification & Architecture Aligned**: API matches [`openapi.yaml`](./openapi.yaml).
