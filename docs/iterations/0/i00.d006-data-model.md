# Data models

| Entity | Fields | Rules & Constraints |
| :--- | :--- | :--- |
| `User` | `id`, `name`, `is_guest` | `is_guest` handles mocked/guest mode now and upgrades later. |
| `Pool` | `id`, `name`, `statement`, `creator_id`, `decider_id`, `deadline`, `winning_outcome_id`, `created_at` | `winning_outcome_id` is `NULL` until the pool is resolved. |
| `Outcome` | `id`, `pool_id`, `label` | |
| `Pick` | `id`, `pool_id`, `user_id`, `outcome_id`, `created_at` | Unique `(pool_id, user_id)`. Tracks which outcome a user selected. |

## Derived state and Logic

### Check score on pool

- Right: `Pick.outcome_id == Pool.winning_outcome_id`
- Wrong: `Pool.winning_outcome_id IS NOT NULL AND Pick.outcome_id != Pool.winning_outcome_id.`

### Pool state

- Open: `winning_outcome_id is NULL and now < deadline`
- Locked: `winning_outcome_id is NULL and now >= deadline`
- Resolved: `winning_outcome_id is NOT NULL.`

## Note on migration path to the Vision

For Iteration 0, the backend sets both `creator_id` and `decider_id` to the
pre-seeded Guest User (`00000000-0000-0000-0000-000000000001`). Identity fields
in a creation request do not override this choice.

The schema can represent a separate decider and more than two outcomes, but
exposing either feature requires corresponding backend rules, API contract,
tests, and UI changes. Iteration 0 accepts exactly two outcomes. Adding a
weight column to `Pick` requires a database migration as well as application changes.
