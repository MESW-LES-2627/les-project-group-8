# Data models

| Entity | Fields | Rules & Constraints |
| :--- | :--- | :--- |
| `User` | `id`, `name`, `is_guest` | `is_guest` handles mocked/guest mode now and upgrades later. |
| `Pool` | `id`, `name`, `statement`, `creator_id`, `decider_id`, `deadline`, `winning_outcome_id` | `winning_outcome_id` is `NULL` until the pool is resolved. |
| `Outcome` | `id`, `pool_id`, `label` | A Pool has 2 rows here for the MVP. |
| `Pick` | `id`, `pool_id`, `user_id`, `outcome_id`, `created_at` | Unique `(pool_id, user_id)`. Replaces your `participants` list. |

## Derived state and Logic

### Check score on pool

- Right: `Pick.outcome_id == Pool.winning_outcome_id`
- Wrong: `Pool.winning_outcome_id IS NOT NULL AND Pick.outcome_id != Pool.winning_outcome_id.`

### Pool state

- Open: `winning_outcome_id is NULL and now < deadline`
- Locked: `winning_outcome_id is NULL and now >= deadline`
- Resolved: `winning_outcome_id is NOT NULL.`

## Note on migration path to the Vision

Backend automatically sets `decider_id = creator_id` when a `Pool` is created. When building the Vision later and letting `User A` assign `User B` as the *decider*, just expose `decider_id` in the UI form. Zero database changes required. The same goes for adding 3+ outcomes or a weight column to `Pick` for weighted pools.
