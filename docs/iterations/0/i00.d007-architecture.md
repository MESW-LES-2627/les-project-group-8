# Iteration 0 architecture and implementation review

Reviewed against local `staging` commit `aaf9b54` on 2026-10-21.
This records current implementation and remaining work; it does not certify the
full Definition of Done or a deployed database.

## Scope and decisions already specified

- The full MVP includes creation, picks, resolution, and a scoreboard. Iteration 0
  implements only creation and listing; these scopes are intentionally different.
- One `Pool` represents one prediction statement, with exactly two outcomes.
  There is no separate question entity in this iteration.
- Authentication is outside the slice. The backend uses the Guest User seeded by
  `backend/migrations/001_init.sql` for both creator and decider.
- `POST /api/pools` accepts `name`, `statement`, `deadline`, and `options`.
  `GET /api/pools` lists newest first. `GET /api/health` checks that Flask responds;
  it does not check database readiness.
- `frontend/src/env.ts` describes a server-only `API_URL`. The intended path is
  browser -> SvelteKit server on Cloudflare -> Flask on Render -> Supabase.
  The checked-in frontend is still a counter page; that integration is pending.

## Part 1: domain rules connected to the existing API

`backend/pool_api/domain.py` owns `NewPool`, `Pool`, `Outcome`, `UserSummary`,
`PoolStatus`, and `ValidationError`. It imports only the Python standard library.
Importing the package no longer imports Flask or constructs an application.

The creation path is:

1. Flask decodes the request body.
2. `NewPool.from_payload` validates and normalizes the creation input.
3. `NewPool.to_payload` adapts it to the existing dictionary-based stores.
4. The existing persistence code creates the pool and outcomes and returns JSON.

Validation rules:

- JSON object; non-blank name and statement, with limits of 120 and 500 characters.
- Exactly two non-blank outcome labels, each at most 100 characters.
- Length limits apply to submitted strings, matching OpenAPI `maxLength`.
  Surrounding whitespace is then trimmed; outcomes are distinct after Unicode
  case folding and trimming.
- A future date-time with an explicit timezone. UTC markers and numeric offsets
  are accepted and normalized to UTC. A date without a time or timezone is rejected.
- Request identity fields cannot replace the server-selected Guest User.

Status is derived, never advanced by a background job: `RESOLVED` when
`winning_outcome_id` is non-null; otherwise `OPEN` before the deadline and
`LOCKED` at or after it. The API recomputes this for in-memory listings too.
Part 1 also fixes serialization of deadlines with negative timezone offsets.
