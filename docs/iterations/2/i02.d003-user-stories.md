# User Stories and Epics

This is the backlog for the MVP described in
[i02.d002-mvp.md](./i02.d002-mvp.md), written after Iteration 0. It covers the
whole MVP journey, not just the next increment.

Each acceptance criterion (AC) is written as Given / When / Then and is intended
to map to one acceptance test, following
[i02.d004-testing.md](./i02.d004-testing.md).

**Status:**

- **Done** — every AC is implemented and covered by acceptance tests, and the
story's *so that* can be demonstrated to a user in the deployed app.
- **Next** — candidate for the next increment.
- **Later** — agreed scope, not yet scheduled.



## Epic map

An epic is a large story; a theme is a collection of related stories. The seven

## Proposed API surface

The stories imply the endpoints below. They are proposals to negotiate, not a
frozen contract; the ACs describe observable behavior and take precedence over
any particular path.


| Method | Path                                         | Stories                                                       |

| `GET`  | `/api/me`                                    | US5 (endpoint done: `{id, name}` of the logged-in User)       |

## E1. Identity & access



### US1: Create an account — Done

Registration does not require email confirmation.

**As** a person new to the app, **I want** to sign up with my email, a password and a display name, **so that** I have my own Account and the pools I create are shown as mine.


| AC  | Given                                | When                                                          | Then                                                                              |
| --- | ------------------------------------ | ------------------------------------------------------------- | --------------------------------------------------------------------------------- |
| 1.1 | I am on the sign-up page             | I sign up with a valid email, a password and the name " Ana " | I am logged in and the header shows "Ana"                                         |
| 1.2 | I just signed up                     | the database is checked                                       | a User exists with my Account's id and the trimmed name                           |
| 1.3 | a blank name                         | I sign up                                                     | I see "Name cannot be empty." and no Account or User is created                   |
| 1.4 | a name longer than 80 characters     | I sign up                                                     | I see "Name must be at most 80 characters." and no Account or User is created     |
| 1.5 | a password under 6 characters        | I sign up                                                     | I see "Password must be at least 6 characters." and no Account or User is created |
| 1.6 | an email that already has an Account | I sign up                                                     | I see "An account with this email already exists." and nothing is created         |




### US4: Enter as the guest user — Obsolete

**As** a visitor, **I want** to use the app as the seeded guest user, **so that**
I can create and see pools without signing up.


| AC  | Given                    | When               | Then                                       |
| --- | ------------------------ | ------------------ | ------------------------------------------ |
| 4.1 | no account or login      | I open the app     | I act as the seeded Guest User             |
| 4.2 | I am acting as the guest | I create a pool    | the guest is stored as creator and decider |
| 4.3 | I am acting as the guest | I browse the pools | no sign-up or login is required            |




### US5: See who I am — Done

**As** a user, **I want** to see which identity the app is using, **so that** I
know whose pools and picks I am looking at.


| AC  | Given                          | When              | Then                                 |
| --- | ------------------------------ | ----------------- | ------------------------------------ |
| 5.1 | the app has an active identity | I open any page   | my name is shown in the layout       |
| 5.2 | the app has an active identity | I reload the page | the same identity is still active    |
| 5.3 | no identity can be resolved    | I open any page   | I am treated as a logged-out visitor |




### US30: Rename my User — Later

**As** a User, **I want** to change my display name, **so that** I can fix a
typo or change how others see me in pools.


| AC   | Given             | When                                                 | Then                                                 |
| ---- | ----------------- | ---------------------------------------------------- | ---------------------------------------------------- |
| 30.1 | I am logged in    | I save a new name with surrounding spaces            | my User has the trimmed name and the header shows it |
| 30.2 | I am logged in    | I save a blank name or one longer than 80 characters | I see an error and my name is unchanged              |
| 30.3 | I renamed my User | anyone views a pool I created                        | it shows my new name as creator                      |

## E2. Create a pool



### US2: Create a two-option pool - Done

**As** a user, **I want** to create a pool with a title, a statement, a deadline and exactly two outcomes, **so that** my friends can predict what will happen.


| AC   | Given                                                            | When                        | Then                                                                                        |
| ---- | ---------------------------------------------------------------- | --------------------------- | ------------------------------------------------------------------------------------------- |
| 2.1  | I am logged in and have valid pool data                          | I create a pool             | the pool is saved as `OPEN`, with me as creator and decider, no winner, and my two outcomes |
| 2.2  | a deadline with a timezone offset                                | I create a pool             | the deadline is stored and returned in UTC                                                  |
| 2.3  | a request that still sends a `creator_id`                        | I create a pool             | I get a 400 error and no pool is created                                                    |
| 2.4  | fewer or more than two outcomes, an empty one, or two equal ones | I create a pool             | I get a 400 error and no pool is created                                                    |
| 2.5  | a deadline that is not in the future                             | I create a pool             | I get a 400 error and no pool is created                                                    |
| 2.6  | a deadline that is not a valid ISO-8601 timestamp                | I create a pool             | I get a 400 error and no pool is created                                                    |
| 2.7  | an empty name or statement, or one that is too long (120 / 500)  | I create a pool             | I get a 400 error and no pool is created                                                    |
| 2.8  | a request body that is not JSON                                  | I create a pool             | I get a 400 error                                                                           |
| 2.9  | I am not logged in, or my token is invalid                       | I create a pool             | I get a 401 error and no pool is created                                                    |
| 2.10 | Ana and Bruno are both logged in                                 | each creates a pool         | each pool has its own creator as creator and decider                                        |
| 2.11 | I am a logged-out visitor                                        | I open the create-pool page | I am sent to log in and brought back to it afterwards                                       |

| 8.2 | an existing pool   | I open it | its outcomes appear in the order they were created                 |

## E4. Pick an outcome



### US10: Pick an outcome — Done

The pick is saved for the logged-in User. A `user_id` in the body is refused, so
a client cannot impersonate another User.

**As** a participant, **I want** to choose one outcome before the deadline, **so
that** I can compete with my friends.


| AC   | Given                                                                  | When                           | Then                                                                         |
| ---- | ---------------------------------------------------------------------- | ------------------------------ | ---------------------------------------------------------------------------- |
| 10.1 | a Bet in an open Pool, an existing User and one of that Bet's Outcomes | I pick that Outcome            | the Pick is saved with the Bet, User, Outcome and time                       |
| 10.2 | I have just picked                                                     | the pool page reloads          | my pick is shown                                                             |
| 10.3 | an unknown pool, or no logged-in User                                  | I pick an outcome              | I get 400 for an unknown pool or 401/403 for no User, and no pick is created |
| 10.4 | an unknown or malformed Outcome id                                     | I pick it                      | I get a 400 error and no Pick is created or changed                          |
| 10.5 | an Outcome from another Bet, including one in the same Pool            | I pick it for the selected Bet | I get a 400 error and no Pick is created or changed                          |




### US11: Change my pick before the deadline — Done

**As** a participant, **I want** to change my pick before the deadline, **so
that** I can correct a mistake or a change of mind.


| AC   | Given                             | When                                         | Then                                        |
| ---- | --------------------------------- | -------------------------------------------- | ------------------------------------------- |
| 11.1 | I have already picked one outcome | I pick the other outcome before the deadline | my pick is replaced, not duplicated         |
| 11.2 | I have changed my pick            | I open the pool                              | only my latest outcome is shown             |
| 11.3 | I have picked                     | I pick again                                 | I still have exactly one pick for that pool |




### US12: See my own pick — Done

The saved pick is read for the logged-in User, the same identity that submits it.

**As** a participant, **I want** to see which outcome I picked, **so that** I can
confirm it or change it.


| AC   | Given                                  | When            | Then                       |
| ---- | -------------------------------------- | --------------- | -------------------------- |
| 12.1 | I have picked an outcome               | I open the pool | my outcome is highlighted  |
| 12.2 | the pool is open and I have not picked | I open the pool | the pick action is offered |
| 12.3 | the pool is locked and I have picked   | I open the pool | my pick is still visible   |




### US13: Be refused a pick after the deadline — Done

**As** a participant, **I want** the app to refuse late picks, **so that** nobody
gains an advantage from hindsight.


| AC   | Given                                        | When                     | Then                                       |
| ---- | -------------------------------------------- | ------------------------ | ------------------------------------------ |
| 13.1 | the deadline has passed                      | I try to pick an outcome | I get a 400 error and no pick is created   |
| 13.2 | the deadline has passed and I already picked | I try to change my pick  | I get a 400 error and my pick is unchanged |
| 13.3 | the deadline is exactly now                  | I try to pick an outcome | the pick is refused                        |




### US14: Be refused an outcome from another Bet — Obsolete

Criteria incorporated into US10.

### US15: See everyone's picks after the deadline — Next

**As** a participant, **I want** to see what everyone picked once picking closes,
**so that** we can compare predictions while we wait for the outcome.


| AC   | Given                                     | When               | Then                                           |
| ---- | ----------------------------------------- | ------------------ | ---------------------------------------------- |
| 15.1 | the deadline has passed                   | I open the pool    | I see each participant's name and outcome      |
| 15.2 | the deadline has passed and nobody picked | I open the pool    | the pick list is empty                         |
| 15.3 | the pool is resolved                      | I open the pool    | the winning outcome is marked                  |
| 15.4 | the deadline has passed                   | I request the pool | the response contains all picks, not just mine |




### US16: Not see others' picks before the deadline — Done

**As** a participant, **I want** everyone's picks to stay hidden until the
deadline, **so that** nobody copies a friend's prediction.


| AC   | Given                                           | When               | Then                                                   |
| ---- | ----------------------------------------------- | ------------------ | ------------------------------------------------------ |
| 16.1 | the deadline is in the future                   | I open the pool    | other participants' outcomes are not shown             |
| 16.2 | the deadline is in the future and I have picked | I open the pool    | my own outcome is still shown                          |
| 16.3 | the deadline is in the future                   | I request the pool | the response does not contain other users' outcome ids |

## E5. Resolve a Bet



### US17: Resolve a Bet by choosing the winner — Next

**As** a decider, **I want** to mark the winning outcome when the event is over,
**so that** everyone can see who was right.


| AC   | Given                                                       | When                                  | Then                                                |
| ---- | ----------------------------------------------------------- | ------------------------------------- | --------------------------------------------------- |
| 17.1 | a Bet with no winner whose Pool deadline has passed         | I resolve it with one of its Outcomes | the winner is stored and the Bet becomes `RESOLVED` |
| 17.2 | a Bet I just resolved                                       | I open its Pool                       | the Bet's winning Outcome is shown                  |
| 17.3 | a Bet I just resolved                                       | I list the Pools                      | that Bet's result is included in its Pool           |
| 17.4 | an Outcome from another Bet, including one in the same Pool | I resolve the selected Bet with it    | I get a 400 error and the result is unchanged       |
| 17.5 | a missing, unknown or malformed winning Outcome id          | I resolve the Bet                     | I get a 400 error and the result is unchanged       |




### US18: Resolve only as the decider — Next

**As** a decider, **I want** only me to settle the pool's Bets, **so that** participants
cannot decide the result in their own favor.


| AC   | Given                          | When                | Then                                        |
| ---- | ------------------------------ | ------------------- | ------------------------------------------- |
| 18.1 | a Bet in a pool where someone else is the decider | I try to resolve it | I get a 403 error and the Bet is unchanged |
| 18.2 | a Bet in a pool where I am the decider | I resolve it | the resolution is accepted |
| 18.3 | an unknown pool or Bet id, or a Bet from another pool | I try to resolve it | I get a 404 response |




### US19: Resolve only after the deadline — Next

**As** a decider, **I want** to be unable to resolve early, **so that** the result
cannot be announced before predictions are locked.


| AC   | Given                         | When                      | Then                                        |
| ---- | ----------------------------- | ------------------------- | ------------------------------------------- |
| 19.1 | the deadline is in the future | I try to resolve a Bet | I get a 400 error and the Bet is unchanged |
| 19.2 | the deadline has passed       | I resolve a Bet           | the resolution is accepted                  |
| 19.3 | the deadline is exactly now   | I resolve a Bet           | the resolution is accepted                  |




### US20: Resolve a Bet only once — Next

**As** a decider, **I want** a result to be final, **so that** Records cannot be
rewritten after the fact.


| AC   | Given                           | When                      | Then                             |
| ---- | ------------------------------- | ------------------------- | -------------------------------- |
| 20.1 | a Bet that is already resolved  | I try to resolve it again | I get a 409 error                |
| 20.2 | a Bet that is already resolved  | I try to resolve it again | the original winner is unchanged |
| 20.3 | a Bet that is already resolved  | I open its pool           | the Bet is still `RESOLVED`      |




### US21: Be refused a winner that is not an outcome — Obsolete

Criteria incorporated into US17.

## E7. Pool structure, Bet types and rounds

These stories describe Pools containing related Bets, following the
[vision domain model](../../diagrams/DomainModel.puml). Each Bet has its own
statement, options and participant Picks. US29 describes named rounds within
a Pool.

### US25: Create a pool as a group of Bets — Done

**As** an organizer, **I want** a Pool with its own name, description and shared
deadline containing related Bets, **so that** friends can follow one event or
competition in a single place.

Only the creator can add Bets, strictly before the Pool deadline.


| AC   | Given                                                      | When                                   | Then                                                                                                    |
| ---- | ---------------------------------------------------------- | -------------------------------------- | ------------------------------------------------------------------------------------------------------- |
| 25.1 | valid Pool details                                         | I create the Pool                      | it has its own ID, name, optional description, creator, creation date and shared deadline, with no Bets |
| 25.2 | my open Pool                                               | I add two Bets separately              | both belong to the same Pool and retain their own statements and ordered options                        |
| 25.3 | a Pool containing several Bets                             | I open its page                        | I see the Pool information and its Bets separately; my Picks remain independent per Bet after reload    |
| 25.4 | existing Pools with statements, options, Picks and results | I access them as Pools containing Bets | their information and associations remain accessible                                                    |




### US26: Create a multiple-choice Bet with n options — Done

**As** an organizer, **I want** to provide two or more possible answers to a
Bet, **so that** predictions are not limited to binary choices.


| AC   | Given                                                    | When                  | Then                                                           |
| ---- | -------------------------------------------------------- | --------------------- | -------------------------------------------------------------- |
| 26.1 | a Bet with two distinct non-empty options                | I save it             | the binary Bet is stored and displayed correctly               |
| 26.2 | a Bet with more than two distinct non-empty options      | I save it             | all its options are stored and displayed in the authored order |
| 26.3 | fewer than two options, blank labels or duplicate labels | I save the Bet        | validation rejects it without partial data                     |
| 26.4 | an open multiple-choice Bet                              | I submit a prediction | exactly one option belonging to that Bet is saved as my answer |




### US27: Display multiple choice as a dropdown — Done

**As** an organizer, **I want** to choose radio buttons or a dropdown for a
multiple-choice Bet, **so that** its options have a suitable presentation.


| AC   | Given                          | When                                             | Then                                                                          |
| ---- | ------------------------------ | ------------------------------------------------ | ----------------------------------------------------------------------------- |
| 27.1 | a multiple-choice Bet          | I choose radio or dropdown presentation and save | that presentation is preserved after reload                                   |
| 27.2 | a Bet configured as a dropdown | a participant opens it                           | the same ordered options appear in a labelled dropdown with no answer assumed |
| 27.3 | either presentation            | a participant submits an answer                  | the same single-choice, identity and deadline rules apply                     |




### US28: Create and answer an open-ended Bet — Later

**As** an organizer, **I want** a Bet that accepts free-text answers,
**so that** I can ask for predictions without enumerating every possible answer.


| AC   | Given                                       | When                  | Then                                                                                      |
| ---- | ------------------------------------------- | --------------------- | ----------------------------------------------------------------------------------------- |
| 28.1 | an open-ended prompt                        | I add it to a pool    | it is saved without requiring an option list and is displayed with a text input           |
| 28.2 | an open Bet and a valid text answer         | a participant submits | the answer is saved for that participant and Bet and remains visible to them after reload |
| 28.3 | an empty/oversized answer or a closed round | a participant submits | the answer is refused without changing an existing prediction                             |


Text limits and correctness criteria remain to be agreed. Free-text answers
follow the same privacy and deadline rules as other predictions.

### US29: Organize multiple rounds in a pool — Later

**As** an organizer, **I want** several named rounds within the same pool,
**so that** recurring events stay in one competition.


| AC   | Given                                   | When                                         | Then                                                         |
| ---- | --------------------------------------- | -------------------------------------------- | ------------------------------------------------------------ |
| 29.1 | an existing pool                        | I add a round with its own deadline and Bets | it is stored in order within that pool                       |
| 29.2 | a pool with several rounds              | participants open it                         | they can distinguish each round's Bets, deadline and results |
| 29.3 | one round is closed and another is open | a participant submits predictions            | only the open round accepts them                             |
| 29.4 | earlier rounds already have predictions | I add another round                          | earlier predictions and results remain unchanged             |

## Open decisions

The following product rules and open questions guide the acceptance criteria.

1. **Blind picks (US16).** Should other participants' picks be hidden until the
  deadline, or public immediately? Hiding is assumed for fairness.
2. **Changing picks (US11).** A participant can replace an earlier choice before
  the deadline.
3. **Deadline boundaries.** Picks are allowed strictly before the deadline;
  resolution is allowed at or after it (US13.3, US19.3).
4. **Who resolves (US18).** The creator is the only person who can choose the
  winning Outcome.
5. **No pick on a resolved Bet (US22).** Counts as neither a win nor a loss; a
  User with no Pick in a Pool is not on its Leaderboard.
6. **Guest participation.** Creating pools, making Picks and resolving require
  a logged-in User; public browsing remains available.
