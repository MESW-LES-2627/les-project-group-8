# How to run tests

## Running them

```bash
cd backend
python -m venv .venv && source .venv/bin/activate
pip install -r requirements-dev.txt
pytest -v
```

Acceptance tests need no Supabase credentials. The two RLS integration tests skip
unless `SUPABASE_URL` and `SUPABASE_PUBLISHABLE_KEY` are set (see `backend/.env.example`). CI runs the same tests, with line and branch coverage (`pytest -v --cov --cov-report=html`, configured in `backend/.coveragerc`), on pushes to
`main`/`staging` and pull requests that touch backend code or the "backend/"
(`.github/workflows/backend-ci.yml`). `render.yaml` configures deployment to wait for passing checks. Each run's job summary shows the coverage table, domain services first, and the HTML report is attached as the `backend-coverage-html` artifact; coverage is reported, not enforced. What it leaves out, and why, is in the [Testing policy](#not-tested-and-why).

## Testing policy

The decisions behind this policy are in the [grilling record](../../assets/iterations/3/grilling-testing-policy-and-coverage.md).

### Tested, by layer

| Layer | Runs | What it is responsible for |
| :- | :- | :- |
| Acceptance (pytest) | `backend/tests/acceptance/`, every backend PR | Every route, service, validation rule and JSON shape, over HTTP, with in-memory repositories and real token verification ([below](#acceptance-tests)) |
| Integration (pytest) | `backend/tests/integration/`, every backend PR | RLS refuses the publishable key ([ADR 0003](../../adr/0003-flask-is-the-only-door-to-app-tables.md)); the JWKS key set is fetched once, refetched once for a new `kid`, and fails clearly ([ADR 0001](../../adr/0001-verify-supabase-tokens-locally.md)) |
| Unit (Vitest) | `frontend/src/**/*.test.ts`, every frontend PR | The pure modules in `src/lib/*.ts` and `src/env.ts` ([below](#frontend-unit-tests)) |
| Component (Vitest browser mode) | `frontend/src/**/*.svelte.test.ts`, every frontend PR | Each Svelte component with a branch, rendered in Chromium: what it shows in each case, its validation messages and its user actions ([below](#component-tests)) |
| End to end (Playwright) | `frontend/e2e/`, PRs touching frontend, backend or `supabase/` | The browser, SvelteKit routes and server code, Flask and a local Supabase built from every migration, together ([below](#end-to-end-tests)) |

### Rules

- A PR that changes behaviour carries its tests, or says here why not ([PR template](../../../.github/pull_request_template.md)).
- A new coverage exclusion is added to the table above in the same PR, naming the automated layer that covers it.
- A hand check is a gap with an open issue, never a reason something counts as covered.
- Coverage is reported, not enforced: no threshold fails a build.

## Acceptance tests

The suite is made of **acceptance tests**: tests check the acceptance criteria from [i03.d003-user-stories.md](./i03.d003-user-stories.md) through the public HTTP API. Payloads are built by test fixtures and the suite does not execute SvelteKit or prove that its actual requests match the API. Tests are written as **Given / When / Then** comments and named after the behavior (`test_pool_naming_its_creator_is_rejected`). The table below links each acceptance criterion to its test.

We test through HTTP because the API is the contract the frontend relies on.
These tests protect the listed behaviors during refactoring and passing them doesn't establish complete OpenAPI conformance or deployed end-to-end functionality.

```
backend/tests/
├── conftest.py                      # fresh app + fake repositories + test token verifier for every test
├── fakes.py                         # in-memory repositories (test doubles)
└── acceptance/
    ├── steps.py                     # sign_in, token helpers, create_pool, create_bet, payloads
    ├── test_us2_create_pool.py      # US2
    ├── test_us3_list_pools.py       # US3
    ├── test_us5_see_who_i_am.py     # US5 backend: GET /api/me and the login guard (#35)
    ├── test_us10_pick.py            # Pick creation/replacement and participant identity
    ├── test_us12_see_pick.py        # US12
    ├── test_us24_other_users_record.py # US24
    ├── test_us26_multiple_choice.py # US26
    ├── test_us27_dropdown.py        # US27
    ├── test_us29_pool_bets.py       # issue #29 / US25: authoring, shared deadline, Bet boundaries

    └── test_jwks_verifier.py        # ADR 0001: the key set is cached and refetched once for a new kid
```

## Fake repositories

`create_app(user_repo=..., pool_repo=..., pick_repo=...)` accepts the repositories it should use. In production it builds the Supabase ones. In tests, `conftest.py` passes in-memory fakes from `tests/fakes.py`, with Pool/Bet creation and reads, and `create_or_replace`/`list_user_picks` for Picks. The fake user repository also has `add`, which `sign_in` uses to seed Users the way the sign-up trigger creates them; the app itself never creates Users.

As a result, everything above the database is real in every test: routes, services, validation, and JSON. The only thing replaced is the storage. Tests are fast, independent, and don't touch the shared Supabase database. The fakes live only in `tests/` and are never used by the running app.

The fakes do not cover Supabase queries, SQL constraints or migration data preservation. The end-to-end suite runs the first two against a local Supabase built from every migration; migration data preservation is a gap (#198).

## The back door (integration)

`tests/integration/test_rls_back_door.py` is the only part of the suite that talks to the real Supabase project. It uses the publishable key, which is public by design, to read and insert `pools` straight through Supabase's REST API, and checks that row-level security refuses both (ADR 0003). The two refusals look different: with no policies, RLS **filters reads** (200 with no rows) but **rejects writes** (Postgres error `42501`). The insert names a User that does not exist, so even if RLS were turned off the foreign key would stop the row being saved and the test would fail with `23503` instead. When the secret key is also set (as in a local `backend/.env`), the read test first checks that pools exist, so an empty answer proves something; CI only has the publishable key and skips that check. Both tests skip when `SUPABASE_PUBLISHABLE_KEY` is not set.

## Access tokens

`create_app(..., token_verifier=...)` also accepts the verifier for Supabase access tokens. `conftest.py` passes one that trusts a throwaway ES256 key pair generated in `tests/acceptance/steps.py`, and the steps sign real tokens with its private half, so the real verification runs. `sign_in(user_repo, name)` seeds a User in the fake repository and returns it with valid auth headers. `expired_token`, `wrong_audience_token` and `forged_token` (signed by a key the app doesn't trust) build the invalid variants.

Fetching Supabase's published key set (`TokenVerifier.from_env()`) is covered by `tests/integration/test_jwks_verifier.py`, against a local key-set server that counts requests: repeated tokens cause one fetch, a token with a new `kid` causes exactly one refetch (once PyJWT's 30 s cooldown has passed; the test drives its clock), an unreachable key set is not reported as a bad token, and a missing `SUPABASE_URL` fails clearly.

## Frontend unit tests

```bash
cd frontend
pnpm install
pnpm test
```

[Vitest](https://vitest.dev/) runs the frontend's pure functions in Node, with no browser and no backend. Its config is the `test` block in `frontend/vite.config.ts`, which has two projects: `server` runs `src/**/*.test.ts` in Node, and `client` runs the [component tests](#component-tests); `pnpm test` runs both. CI runs `pnpm test --coverage` after the type-check (`.github/workflows/frontend-ci.yml`). Each run's job summary shows the per-file line and branch coverage table, and the HTML report is attached as the `frontend-coverage-html` artifact; coverage is reported, not enforced. It measures `src/lib/*.ts`, `src/env.ts` and the components in `src/lib/components/`: routes, `hooks.server.ts` and `lib/server/` are left out because e2e covers them, and `types.ts` and `index.ts` because they hold only types and re-exports. A module with no unit test, such as `account.ts`, stays in and shows as a gap. Each test file sits next to the module it tests:

| Test file | Module | What it checks |
| :- | :- | :- |
| `src/lib/format.test.ts` | `format.ts` | `formatDeadline` in UTC and on invalid input; `toLocalInput` and `localInputToIso` round trip in any timezone, and reject empty or invalid input |
| `src/lib/redirect.test.ts` | `redirect.ts` | `loginPath` keeps path and query; `sameSitePath` sends `https://evil.com`, `//evil.com`, `/\evil.com`, relative paths and `null` to `/` (open redirect) |
| `src/lib/form.test.ts` | `form.ts` | `readField` for a text field, a missing key and a file |
| `src/lib/pool.test.ts` | `pool.ts` | the new-Pool form's `validatePool`: each error, the 120/500 limits, and a past or present deadline with the clock fixed by `vi.setSystemTime` |
| `src/env.test.ts` | `env.ts` | `API_URL` and `SUPABASE_URL` keep only the origin, are `undefined` when empty, and report a bad URL |

### Component tests

The `client` project renders Svelte components in Chromium, through [Vitest browser mode](https://vitest.dev/guide/browser/) with the Playwright provider and [`vitest-browser-svelte`](https://github.com/vitest-community/vitest-browser-svelte). Run them with the unit tests (`pnpm test`); they need Chromium once (`pnpm exec playwright install chromium`), which CI installs. Each test file is `<Component>.svelte.test.ts`, next to its component.

A component gets tests when it has a branch: something shown only in some cases, input validation, or a user action. Components that only display data (`PoolCard`, `StatusBadge`) have none and show as gaps. Tests set the route's data by mocking `page` from `$app/state`. `src/lib/components/form-actions.mock.ts` stands in for `enhance` and `invalidateAll`, so a submit stays pending until the test finishes it as a success or a failure; the real round trip to the server is e2e's.

Closed or resolved Bet: the User's pick or that they made none, the winner marked |

| `CorrectPickers.svelte.test.ts` | Only the Users who picked this Bet's winner, the empty message, hidden with no winner, while the Pool is open, for a visitor, or when Picks failed to load |
| `Leaderboard.svelte.test.ts` | The empty message, the entries with the current User marked |

## End-to-end tests

```bash
cd frontend
pnpm install
pnpm exec playwright install chromium
pnpm test:e2e
```

[Playwright](https://playwright.dev/) drives Chromium through the real app: SvelteKit (`vite preview`), Flask and Supabase. Supabase is a throwaway local stack ([ADR 0005](../../adr/0005-e2e-tests-use-a-throwaway-local-supabase.md)), so running them needs Docker and the [Supabase CLI](https://supabase.com/docs/guides/local-development/cli/getting-started). `frontend/e2e/run.sh` starts the stack with ES256 signing keys and email confirmation off (`supabase/config.toml`), applies every file in `backend/migrations/` in sorted order, runs the specs, and removes the stack. `frontend/playwright.config.ts` starts Flask (from `backend/.venv` when it exists) and the frontend. Each test signs up its own Accounts, so tests never share data. Until Resolution has a UI (#73), `e2e/leaderboard.spec.ts` writes its Users, passed deadline, Picks and winning Outcomes straight to the local database with its secret key; the browser only reads. CI runs the suite on pull requests that touch the frontend, the backend, `supabase/` or the workflow (`.github/workflows/e2e.yml`); it is not a required check yet.

| Spec | What it checks |
| :- | :- |
| `e2e/signup.spec.ts` | a new visitor signs up and the header shows their name (US5) |
| `e2e/session.spec.ts` | log in, the session survives a reload, log out; an expired session that can't be renewed and a forged access token both send the create-pool page to login; a logged-out visitor is sent to login and back (AC 2.11) |
| `e2e/pools.spec.ts` | a new Pool is created empty and shows its name, description and deadline; the pick/detail flow; another User sees neither the creator's Picks nor the authoring controls, and each keeps their own Pick (AC 16.1–16.2); a dropdown Bet's labelled, ordered Outcomes with none selected (AC 27.2) |
| `e2e/leaderboard.spec.ts` | after the deadline, a User sees every Record, ranked by wins then fewer losses, with ties sharing a rank (AC 24.1, 31.1–31.3); a Pool with no Picks shows an empty Leaderboard (AC 31.4); before the deadline, a Pool with Picks shows no Leaderboard (AC 31.6) |
