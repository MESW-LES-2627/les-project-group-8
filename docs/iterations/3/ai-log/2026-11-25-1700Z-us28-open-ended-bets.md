# Implement US28 open-ended Bets with the Strategy pattern

- **Who:** João Cerqueira.
- **Tools:** Claude Code desktop app (Claude Opus 5.5).
- **Outcome:** Free-text Bets end to end for [US28 #179](https://github.com/MESW-LES-2627/les-project-group-8/issues/179), and the Strategy pattern documented in [design.md §5.1](../../../design.md#51-strategy--validating-a-picks-answer-by-the-bets-answer-type).
- **Delegated:** Read the issue and the Iteration 2 Scenario 2 decision, proposed a plan and the pattern, then wrote the migration, backend (`picks/answers.py` strategies, typed `Pick.answer`, `answer_type` on Bets, text Bets refused by Resolve), frontend (answer-type toggle, text input, revealed answers), OpenAPI changes, tests, the design-pattern section and its UML diagram.
- **What we decided ourselves, and why:** The user required a design pattern documented in design.md and approved the plan before any code was written. Strategy follows the decision the team recorded in Scenario 2, rather than a pattern picked to satisfy the requirement.
- **How we checked:** Backend `pytest`: 182 passed, 2 skipped (integration) after the test cleanup below. Acceptance tests cover AC 28.1–28.10. The frontend `svelte-check`, vitest and the new Playwright test were not run locally (no Node on the machine); CI runs them.
- **Notes:** AC 28.9 says "a visitor"; listing Picks still requires login, as for choice Bets (US15), so the test uses a third signed-in User. The browser text input has no `maxlength`, because browsers count UTF-16 units while the API counts code points; the SvelteKit action checks code points.
- **Follow-up:** At the user's request, the Strategy interface changed from a `typing.Protocol` (implemented implicitly) to an explicit `abc.ABC` that each validator subclasses, so the code shows the interface implementation that the UML draws. A unit test checks that the interface and incomplete subclasses cannot be instantiated.
- **Where it was wrong:** The assistant wrote backend unit tests although [the testing approach](../i03.d004-testing.md#acceptance-tests) uses acceptance tests through the HTTP API, and over-tested: 32 acceptance cases where the ACs need far fewer, plus 22 unit cases repeating them. It also forgot to mark US28 Done and to add its rows to the AC table. At the user's request it deleted the unit tests, trimmed the US28 file to 13 tests (19 cases) and made both documentation updates.
- **Merge with the testing policy:** After staging gained [the testing policy](../i03.d004-testing.md#testing-policy), the user said it takes priority over this branch's edits to d004. The assistant merged staging, kept staging's d004 and added only the US28 rows, replaced links to the removed `#what-we-test-and-why` heading, and dropped `#L` line fragments from design.md's code links in case the docs-links check rejects them. Per the policy's component rule, it fixed the component-test fixtures broken by the new `answer_type` and `answer_text` fields and added one case per new free-text branch in `BetCard`, `BetForm`, `BetPicks` and `ResolveControl`, plus a `US28` story in `e2e/stories.story.ts`. Checked locally: `pnpm check` (0 errors), `pnpm test` (99 passed), backend `pytest`, and a script that checked the touched docs' local links and anchors. Not run locally: the e2e suite and the story (no Supabase CLI or usable Docker) and lychee itself.
